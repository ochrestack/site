How Scrollgrep was tested

What was run, what was not, and the numbers, each with the version it was measured on. Back to the Scrollgrep product page or the quick start.

What was run (Linux)

  • IntelliJ IDEA 2025.3: the plugin's test suite (138 tests, headless, with real Bash, Zsh and sh terminals), and the window, with Scrollgrep 1.1.7 installed from the zip.
  • IntelliJ IDEA 2026.3: the free filter on fast output with both of its terminal emulators, Preview, and the pictures on the product page (Scrollgrep 1.1.7).
  • PyCharm 2026.3: install, the filter and Preview with the Python sample job (Scrollgrep 1.1.7). PyCharm 2025.3: install and the filter (Scrollgrep 1.1.1).
  • WebStorm 2025.3: the same test suite (129 tests then), run headless on WebStorm's own platform; no window was opened (Scrollgrep 1.1.6). WebStorm 2026.3: started headless with Scrollgrep installed from the zip; it loaded, and no filter was run (Scrollgrep 1.1.6).
  • JetBrains' Plugin Verifier finds Scrollgrep compatible with IntelliJ IDEA 2025.3 and 2026.3 and WebStorm 2026.3.

What was not run

WebStorm's window and the filter in WebStorm 2026.3 (the window starts only after a JetBrains Account login), GoLand and the other JetBrains IDEs, Windows, macOS, PowerShell, Remote Development, and a real Marketplace trial or purchase.

Measured

  • Scrollgrep 1.1.7, IntelliJ IDEA 2026.3, Linux. Five Gradle test runs with the debug log, about 11,000 lines: 70 of 70 lines with "failed" listed by Scrollgrep, 49 found by the Terminal's own search (it found between 35 and 49 across our runs of the same five). cat of a 97,317-line sync log on the Ghostty emulator: 874 of its 10,470 "skipped row" lines kept, marked "some lines missing"; after switching new tabs to JediTerm, the same cat kept 10,470.
  • Scrollgrep 1.1.0, IntelliJ IDEA 2025.3, headless, Linux, 4 CPUs. 200,000 lines at full speed in a real Bash tab, five runs. Each run: 2,061 matching lines, the same as grep -c. Matches appeared a median of 0.52 to 0.66 s after they were printed, and the longest block of the UI thread while they were added was 65.7 ms.
  • Scrollgrep 1.1.3, IntelliJ IDEA 2026.3 with its windows, Linux. Each command in a new tab with the filter set first. Five Gradle test runs: 70 of 70 (the Terminal's own search found 35 in that run). tail -f of a sync log written at about 4,000 lines a second: 10,470 of 10,470. On the Ghostty emulator at full speed: cat of that sync log kept 988 of 10,470 (the Terminal itself held 859 at the end), cat of the Gradle log 35 of 70, the 200,000-line generator 85 of 2,062, each marked "some lines missing". In new tabs on JediTerm: 10,470, 70 and 2,062, every line.

How much the Ghostty emulator skips changes from run to run: 874, 918 and 988 of the same 10,470 lines were kept in three runs.

Fast output on IDE 2026.3

The 2026.3 IDEs start new Terminal tabs on the Ghostty emulator. When output prints faster than it can show it (a cat of a large file, a generator at full speed), the Terminal shows only its screen until the output pauses, then the last few thousand lines: what scrolled past in between never reaches the Terminal's text, so no plugin can read it. Scrollgrep keeps every line that does arrive, in order, and lines up what the Terminal sends after a pause with what it already holds, so a build with pauses between bursts loses nothing. Where lines are missing, the results show ⋯ the Terminal skipped lines here ⋯, the status line says "some lines missing", and the panel offers use JediTerm for new tabs.

That link switches the IDE's own setting (Registry: terminal.use.ghostty.emulator) off, and only when you click it. New tabs then run on the JediTerm emulator, as in 2025.3, which passes every line on; no restart is needed. Open a new tab and run the command again. To switch back: Find Action (Ctrl+Shift+A), Registry…, tick terminal.use.ghostty.emulator.
