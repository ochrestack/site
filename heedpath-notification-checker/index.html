Heedpath – Notification Checker for Jira

When someone says “I never got the email”, Heedpath shows a Jira Cloud admin whether the notification scheme and permissions send that event to them, and the line that decides it.

  • “Why didn't they get the email?” One of three answers, Notified, Not notified or Cannot tell, with the scheme line that decides it, the person's access to the issue (issue security included) and their account.
  • “Some team members are notified and some not.” Who gets this lists everyone one event reaches on an issue, each with the lines that include them, and who drops out, and why.
  • “We need to confirm it to the client.” Copy answer puts the whole answer in the ticket as plain text. It says what the configuration sends, never that an email was delivered.

How it works

  1. Pick an issue, a person and an event.
  2. Heedpath reads the scheme, roles, groups, watchers, issue security and the account. It changes nothing.
  3. One answer, with the line that decides it, ready to copy.

In Jira

Heedpath's page lives inside Jira, so its screenshots are taken on a live Jira site; they follow from the run on our test site. Each frame names the screen it will hold.

What it does

  • Check one person: every line of the event's row, all twelve recipient types, each with the fact that includes or excludes the person (“in project role Developers through group dev-team”), then their access and account. Customer accounts and accounts without Jira product access are never “Notified”, and the answer says why.
  • All events: what one person will and will not hear about on one issue.
  • Who gets this: groups over 1,000 members show as a count until you press Show members.
  • From the issue: Check notifications in the issue's ••• menu, for Jira admins.
  • Says what it cannot see: personal notification settings, email delivery, @mention emails, Jira Service Management customer notifications and which event a transition fires, each with the route to check it. Missing data gives Cannot tell, never a guess.
What Jira already does. Jira already lets an admin find the answer by hand: open the project's notification scheme, read the event's row, then check the person against each entry (role members on the People page, group members in user management, the issue's watchers, custom field values), then check their access with the Permission helper. Atlassian's own recommendation since the 2024 removal is to log in as the person and look at their notification settings. For one simple case on a small site that is enough. Heedpath does the whole chain in one answer.

Known limits

Reads configuration, not deliveries: “Notified by the scheme” is not a record of an email. Company-managed projects only (team-managed gets Cannot tell); Jira Cloud and English only; Jira admins only; reads Jira as it is now, not as it was. All limits, and how to read an answer: the quick start.

How we tested

160 automated tests pass headless (Node 22, Linux) against a model of Jira Cloud's REST API built from Atlassian's reference, including 69 expected answers written by hand and a 1,203-member group. The built page passed 14 checks in Chromium outside Jira. Not yet run on a live Jira site, inside Jira's own page, or in Windows or macOS browsers; that run and the screenshots come before the Marketplace.
